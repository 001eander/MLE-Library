# AutoResearch

[![项目概览](https://github.com/karpathy/autoresearch/raw/master/progress.png)](https://github.com/karpathy/autoresearch/blob/master/progress.png)

> 曾几何时，前沿 AI 研究是由肉计算机完成的——它们要在吃饭、睡觉、享受其他乐趣，以及偶尔通过声波互连在“小组会议”仪式中同步的间隙来做研究。那个时代早已远去。如今，研究已完全成为自主 AI 智能体集群的领域，这些集群运行在天空中的计算集群巨型结构之上。这些智能体声称，我们现在已处于该代码库的第 10,205 代；无论如何，没人能判断这是对是错，因为“代码”如今已是一个自我修改的二进制文件，其复杂程度已超出人类理解。这个仓库讲述了这一切是如何开始的。——@karpathy，2026 年 3 月。

这个想法是：给 AI 智能体一个小规模但真实的 LLM 训练环境，让它在夜间自主实验。它会修改代码，训练 5 分钟，检查结果是否有提升，保留或丢弃，然后重复。早上醒来时，你会看到一份实验日志，并且（但愿如此）得到一个更好的模型。这里的训练代码是 nanochat 的简化单 GPU 实现。核心思想是，你不再像通常作为研究者那样直接改动任何 Python 文件。相反，你要编写 `program.md` Markdown 文件，为 AI 智能体提供上下文，并搭建你的自主研究组织。本仓库中的默认 `program.md` 有意保持为极简基线，不过，如何随着时间迭代它，以找到能实现最快研究进展的“研究组织代码”、如何加入更多智能体等，显然都是可以做到的。关于这个项目的更多背景见这条推文和这条推文。

## 工作原理

该仓库有意保持精简，真正重要的文件只有三个：

- `prepare.py`：固定常量、一次性数据准备（下载训练数据、训练 BPE 分词器）以及运行时工具（数据加载器、评估）。不修改。
- `train.py`：智能体编辑的单个文件。包含完整的 GPT 模型、优化器（Muon + AdamW）和训练循环。一切都可以调整：架构、超参数、优化器、批大小等。该文件由智能体编辑并迭代。
- `program.md`：面向单个智能体的基线指令。把你的智能体指向这里，然后放手让它运行。**该文件由人类编辑并迭代。**

按照设计，训练运行采用固定的 **5 分钟时间预算**（实际耗时，不含启动和编译时间），无论你的算力细节如何。指标是 `val_bpb`（验证集每字节比特数），越低越好，并且与词表大小无关，因此可以公平比较架构变更。

如果你是神经网络新手，这份[“新手指南”](https://x.com/hooeem/status/2030720614752039185)看起来相当不错，可以提供更多背景信息。

## 快速开始

**要求：** 单块 NVIDIA GPU（已在 H100 上测试）、Python 3.10+、[uv](https://docs.astral.sh/uv/)。

```bash
# 1. 安装 uv 项目管理器（如果尚未安装）
curl -LsSf https://astral.sh/uv/install.sh | sh

# 2. 安装依赖
uv sync

# 3. 下载数据并训练分词器（一次性，约 2 分钟）
uv run prepare.py

# 4. 手动运行一次训练实验（约 5 分钟）
uv run train.py
```

如果上述命令都能正常执行，说明你的环境配置可用，你可以进入自主研究模式了。

## 运行智能体

只需在这个仓库中启动你的 Claude、Codex 或任何你想用的工具（并禁用所有权限），然后就可以这样提示：

```text
请先查看 program.md，然后开始一项新实验！先完成环境配置。
```

`program.md` 文件实质上是一个超轻量级的“技能”。

## 项目结构

```text
prepare.py      — 常量、数据准备和运行时工具（不要修改）
train.py        — 模型、优化器、训练循环（由智能体修改）
program.md      — 智能体指令
pyproject.toml  — 依赖
```

## 设计选择

- **单一修改文件。** 智能体只改动 `train.py`。这使范围保持可控，代码差异也便于审查。
- **固定时间预算。** 无论你的具体平台如何，训练始终恰好运行 5 分钟。这意味着你可以预期大约每小时 12 次实验，睡眠期间大约 100 次实验。这个设计决策有两个好处。第一，无论智能体更改什么（模型大小、批大小、架构等），实验都具有直接可比性。第二，这意味着 autoresearch 将在这段时间预算内为你的平台找到最优模型。缺点是，你的运行及结果无法与其他人在其他计算平台上运行的结果进行比较。
- **自包含。** 除 PyTorch 和少数小型软件包外，没有外部依赖。没有分布式训练，没有复杂配置。一个 GPU、一个文件、一个指标。

## 平台支持

此代码目前要求你拥有一块 NVIDIA GPU。原则上完全可能支持 CPU、MPS 和其他平台，但这也会使代码膨胀。我现在并不 100% 确定自己是否想亲自承担这项工作。人们可以引用（或让他们的智能体引用）具有更广泛平台支持的完整父级 nanochat 仓库，其中展示了各种解决方案（例如 Flash Attention 3 内核的回退实现、通用设备支持、自动检测等）。欢迎为其他平台创建分支或讨论，我很乐意在说明文档中新增的“值得关注的分支”部分等处链接到它们。

考虑到似乎有很多人想在比 H100 小得多的计算平台上折腾 autoresearch，我再补充几句。如果你打算在更小的电脑（MacBook 等）上尝试运行 autoresearch，我推荐使用下面某个分支。除此之外，对于想要创建分支的人，这里还有一些关于如何为规模小得多的模型调整默认值的建议：

1. 为了获得勉强像样的结果，我会使用熵低得多的数据集，例如这个 [TinyStories 数据集](https://huggingface.co/datasets/karpathy/tinystories-gpt4-clean)。这些是 GPT-4 生成的短篇故事。由于数据范围窄得多，你将能用小得多的模型看到合理的结果（如果你在训练后尝试从中采样）。
2. 你可以尝试降低 `vocab_size`（词表大小），例如从 8192 降到 4096、2048、1024，甚至直接使用字节级分词器，将 UTF-8 编码后的 256 种可能字节作为词表。
3. 在 `prepare.py` 中，你需要大幅降低 `MAX_SEQ_LEN`，根据电脑性能甚至可以降到 256。降低 `MAX_SEQ_LEN` 后，你可能需要尝试略微增大 `train.py` 中的 `DEVICE_BATCH_SIZE` 来补偿。每次前向和反向传播处理的词元数量是这两者的乘积。
4. 同样在 `prepare.py` 中，你需要减小 `EVAL_TOKENS`，以便在更少的数据上评估验证损失。
5. 在 `train.py` 中，控制模型复杂度的主要参数是 `DEPTH`（这里默认为 8）。许多变量都是它的函数，因此可以将其降到 4 左右。
6. 你很可能需要将 `WINDOW_PATTERN` 设为 `"L"`，因为 `"SSSL"` 使用交替的带状注意力模式，在你的设备上可能效率很低。可以尝试一下。
7. 你需要大幅降低 `TOTAL_BATCH_SIZE`，但应保持为 2 的幂，例如降到 `2**14`（约 16K）左右，具体数值很难确定。

我认为这些是合理的超参数调整方向。可以向你常用的编程智能体求助，把这份指南和完整源代码复制给它。
