# 代码空间搜索与解树（Code-Space Search / Solution-Tree Search）

把「机器学习工程」从「调参/选模型」改写为「在一个程序空间里搜索」：解就是代码，目标是让它在一个标量指标上更好，搜索过程被组织成一棵记录改进关系的树。本页以 AIDE 为参照实现（[[aide]]），以 AlphaEvolve 的进化式程序数据库（[[alphaevolve]]）与 autoresearch 的单链贪心（[[autoresearch]]）作为对照，先给来源论述，再给跨来源的综合与待验证假设。

## 来源论述（AIDE）

**问题框架**。传统 AutoML、NAS、超参优化都依赖**预定义的配置搜索空间**：定义空间需要领域专家，搜索算法常被批评为「相对人类专家偏暴力」，算力效率低且有验证集过拟合风险（[[aide]], p. 1）。论文的反命题：LLM 的编码能力让搜索**直接发生在代码空间**，模型自带的领域知识把候选范围收窄，从而提升样本效率，并有望处理深度学习这类算力密集任务（p. 1–2）。

**形式化**。解空间 `S`（如 Python 脚本）、无状态目标 `h : S → R`，目标 `s* = argmax_{s∈S} h(s)`（式 (1)，p. 2）；根解 `s₀` 为空脚本；解树 `T` 的节点是脚本、边是改进尝试；策略 `π(T)` 选基准解，编码算子 `f(s, Σ(T))` 产出新解，摘要算子 `Σ(T)` 把树压缩成 prompt 可承载的上下文（p. 3–4）。算法 1 每轮做四件事：提议 → 评估 → 挂树 → 换基准（p. 3）。

**为什么要树而不是「历史全塞」**。论文把 ReAct 式 agent 归为 POMDP 框架：状态是全部历史观测，缺少在结构明显时拆解问题的原则性办法，而且「不断追加历史会让 prompt 过大、context 最终填满」（p. 2）。改成树 + 无状态评测后，每个节点独立可评、可比较，也因此可以并行或断点续跑（本段后半句为综合）。

**归因优先的算子设计**。improve 只提**恰好一个原子改动**（换优化器、加正则），理由是让「该改动对性能的影响可直接测量」（p. 4）。debug 则明确要求**保留整体思路**，只修 import、张量维度之类错误（p. 3）。这两条把「一次实验一个变量」从人的纪律变成了算子约束。

**记忆的压缩形态**。`Σ(T)` 只抽取三类信息：性能指标、超参设置、调试线索（如 traceback 里错位的数组形状），从而在「不炸大 prompt」的前提下保留先验（p. 4）。此外每个 prompt 都带一小段静态数据预览（行数、列名、划分），足以支撑验证集划分、超参缩放等决策，但不是完整 EDA（p. 4）。

## 综合

### 1. 五种搜索空间的组织方式

| 组织方式 | 搜索空间来源 | 记忆载体 | 代表 |
| --- | --- | --- | --- |
| 配置空间搜索 | 人预先定义（算法、网格、架构原语） | 无（每次试验独立） | AutoML / NAS / HPO（[[aide]], p. 1） |
| 代码空间树搜索 | LLM 的先验隐式给出候选更新 | 解树 + `Σ(T)` 摘要 | AIDE（p. 3–4） |
| 经验库 / 灵感队列 | 同上，但候选更新由「从历史合成的灵感」驱动 | 全量 solution、日志、评估结果 | Hyra-1.0（[[experience-bank]]、[[hyra-1-0]]） |
| 程序数据库 / 进化 | 同上，候选由「从历史程序采样的提示 + 多模型生成」得到 | 程序数据库（实现进化算法，按评估器分数选择） | AlphaEvolve（[[alphaevolve]]） |
| 单链贪心（keep/discard） | 同上，但只以「当前最好」为基准 | 工作区当前文件 + 实验日志（历史不参与选点） | autoresearch（[[autoresearch]], L19、L74） |

差别不在「要不要 LLM 写代码」，而在**把哪些历史压成什么形状喂回去**：树 + 摘要保留父子归因关系；种群强调多样性；经验库强调全量可重放；单链贪心则**基本不喂历史**——只保留一个当前最优文件，靠人维护的指令文件（`program.md`）维持方向（综合）。

**两类单文件代码搜索的结构差异**（两者都是「单文件可改、外部评估」的形态）：

| 维度 | AIDE 解树（[[aide]]） | autoresearch 单链（[[autoresearch]]） |
| --- | --- | --- |
| 改动粒度 | improve 恰好一个原子改动（p. 4） | 整次运行：一处或多处均可（图内标签含 `halve total batch` 与 `warmdown` 这类复合改动） |
| 历史结构 | 树：节点是解，边是一次改进尝试（p. 3） | 无结构；只有 running best 与实验日志（L19） |
| 评估单位 | 节点分数（脚本跑一次） | 每次实验固定 5 分钟墙钟（L29） |
| 可比性来源 | 同一评估器版本 + 同一数据划分 | 固定时间预算（代价：跨平台不可比，L75） |
| 失败回退 | 回到父节点或另一个分支 | 回到当前最好；丢弃即丢失 |
| 指标 | 任务指标（如 `Exceeds % of Humans`） | `val_bpb`（与词表大小无关，L29） |

**进化式程序数据库与解树的结构差异**（依据 [[alphaevolve]], L25–L31、L57）：

| 维度 | AIDE 解树（[[aide]]） | AlphaEvolve 程序数据库（[[alphaevolve]]） |
| --- | --- | --- |
| 历史结构 | 树：节点是解，边是一次改进尝试（p. 3） | 程序数据库 + 进化选择，决定哪些程序进入后续提示（L29 图注） |
| 改动粒度 | improve 恰好一个原子改动（p. 4） | 一次可同时改优化器与权重初始化、损失函数、超参扫描；示例需 15 次变异（L57） |
| 作用域 | 单文件 Python 脚本（p. 3） | 整个代码库（L25） |
| 多样性来源 | 初始 draft 铺开 + 硬编码策略 | 多模型分工：Flash 增广度、Pro 增深度（L27） |
| 评估 | 节点自选划分 + 外部 holdout（p. 5） | 每问题定制评估器，自动打分（L31） |
| 公开程度 | 论文 + 开源实现 | 博客 + 白皮书，无实现、无版本 |

本库判断（**综合**）：两者的差别不只是「树 vs 种群」，而是对「改进是否可分解」的假设不同。原子改动假设改进可以逐步叠加，因此父子归因最有价值；全代码库变异假设最优解需要多处协同修改，分步走会困在局部最优——AlphaEvolve 的矩阵乘法发现正是这种形态（一次发现涉及优化器、权重初始化、损失函数与超参扫描）。这条假设尚无同预算对照。

### 2. 原子改动的收益与代价

- 收益：每次改进可归因，天然带有「单变量对照」的性质；坏改动容易回退（回到父节点）；也便于把节点分数直接当排序依据。
- 代价：一次只改一处时，需要**多步交互**才能成立的改进（跨文件重构、需要先改接口再改实现）几乎无法被表达。AIDE 在 RE-Bench 的失败正是这个形态：需要大代码库改动或多步交互的任务上「反复打局部补丁，而不去发现新策略」（p. 9）。
- 图 4 的读数支持这一点：AIDE 的分数在约 5 小时后基本不再上升（≈0.36），而人类在 6 小时后继续爬升到 ≈0.65（p. 9，已目视核查）。来源把原因归为「简单贪心策略可能导致局部最优」（p. 9 图注，来源论述）；**「平台期=局部最优」仍是解释而非测量**，属于待验证假设。
- 反例（autoresearch 的单链贪心）：它连「原子」约束都没有，一次可改多处，因此**无法把分数变化归因到某一处改动**；代价换成了另一件事——每个被保留的改动都必须整体回退（[[autoresearch]], L19、L74）。AIDE 图 4 与 autoresearch 进度图的平台段形态相似（前者约 5 小时走平，后者第 43–64 次实验约 20 次无改进），但两图的预算语义、指标与任务均不同，不能并列比较（综合）。

### 3. 摘要即记忆，但有损

`Σ(T)` 与 Hyra-1.0 的经验库是两种相反取舍：前者**有损压缩**（只留指标、超参、调试线索），换来 prompt 恒定长度与「节点无状态」；后者**全量保存**（solution、日志、源码），换来可重放但要靠检索/合成来控制上下文（[[experience-bank]]）。选哪种取决于两件事：历史是否需要被审计复算（需要 → 全量）、以及单次尝试的 token 成本是否主导预算（主导 → 压缩）。这一取舍在现有来源中都只有机制论证，没有对照实验。

### 4. 失败模式清单

| 失败模式 | 表现 | 来源中的证据 |
| --- | --- | --- |
| 局部最优 / 平台期 | 分数长时间不动，仍在同一父节点附近微调 | RE-Bench：Rust CodeContests 反复局部补丁（p. 9） |
| 表达力不足 | 需要多文件、多步交互的改动无法被单次原子编辑表达 | 同上（p. 9） |
| 验证集过拟合 | 树在固定划分上搜索，节点分数即选择依据 | 来源自述「过拟合验证集」风险与 holdout/private 集差异（p. 1、p. 7） |
| 代码膨胀 | 步数增加后代码复杂度上升，可能掩盖「到底改了什么」 | Fig 6：复杂度 ≈1.0→1.6（18 步，p. 15，已目视核查） |
| 摘要丢信息 | `Σ(T)` 只保留指标与线索，某些跨分支的隐含约束会丢失 | 来源未讨论；属综合推断 |
| 种群多样性塌缩 | 选择只按分数时，候选收敛到少数模式，探索失效 | 来源未讨论；属假设（[[alphaevolve]] 未披露选择机制） |
| 全代码库变异的可运行性风险 | 一次多处修改可能破坏可执行性，需要额外修复轮次 | 来源未讨论；属综合推断 |
| 噪声选择（winner's curse） | 在单次运行的点估计上做 keep/discard，改进幅度与种子波动同量级时仍会稳定「保留」 | autoresearch 进度图把 `random seed 42→137` 计为改进（[[autoresearch]]「图表核查」）；属综合推断 |
| 历史丢失 | 只保留 running best，被丢弃分支的经验不留，无法从失败回退点继续 | autoresearch 无树/无种群（L19）；属综合推断 |

## 工程清单（综合）

- **先固定评估契约再建树**：`h` 的输入不可见标签、输出必须标量且可复算；节点分数只在同一评估器版本内可比。
- **给「原子」下定义**：允许一次改动触及多少行、几个函数、几个文件；这个定义直接决定搜索能表达什么。
- **为整树设预算而非为单次调用设预算**：树搜索的收益来自「多次便宜尝试」，因此要限制总步数、单节点时限与调试深度，而不是只限 token。固定墙钟预算（autoresearch 的 5 分钟）是另一种写法：它让「任意改动之间可比」，但代价是**跨平台不可比**（[[autoresearch]], L29、L75）；要跨平台比较就得改成固定步数或固定 token 数。
- **保留父子关系**：树结构本身就是审计日志；压缩进 prompt 的摘要不能替代持久化的树。
- **定期从「最好的节点」重新 draft**：来源的硬编码策略只有 draft/debug/improve，没有「从头换路线」的机制，这是平台期的结构性原因之一（综合）。

## 假设（待验证）

1. 原子改动带来的可归因性，比「一次改多处」的更高上限更重要——即长期期望收益更高。现有证据只是 AIDE 与其它脚手架的整体比分，缺少控制变量的对照。
2. 平台期主要由「策略只有 improve」造成，而非底层模型能力上限；若是前者，加入「重新 draft / 换路线」应能突破。
3. `Σ(T)` 的压缩损失对结果影响不大（因为节点可重放）；未验证。
4. 树搜索优于「上下文累积」的优势会随上下文窗口变大而缩小；未验证。
5. 当改进需要多组件协同（优化流程、kernel/编译管线）时，程序数据库/种群优于单谱系解树；当改进可分解为独立小步时，原子改动的评估效率更高。两者应在同一评估预算下比较，目前无对照。
6. 广度/深度模型分工（Flash 探索 + Pro 给方向）比单一强模型更省评估预算；[[alphaevolve]] 未做消融。
7. AlphaEvolve 相对 AIDE 的关键差异是「整个代码库」的作用域与协同改动能力，而非底层模型更强；未验证。

## 待解问题

- 树搜索与「多臂/进化」策略在同一预算下的对照缺失：AIDE 只有硬编码 `π`，没有与 UCB、beam、进化选择比较。
- 「节点无状态」在依赖环境副作用（缓存、随机种子、数据顺序）的任务里是否成立？论文未讨论可复现性设置。
- 如何检测「分数上升但实际退步」（reward hacking）？AIDE 论文没有专门的检测机制讨论，见 [[evaluator-design-and-reward-hacking]]。
- 代码复杂度上升是能力增长的副产品还是失控信号？Fig 6 只给趋势，没有与分数做相关分析。
- AlphaEvolve 的进化选择机制（种群规模、选择压力、多样性维护）未披露，无法判断它是「按分数 top-k」还是别的策略。
- 「全代码库变异」如何保证每一代程序仍可运行？博客只给结果，未描述修复、回滚或可行性过滤。
- 单链贪心（autoresearch）与解树（AIDE）在同一任务、同一预算下谁更好？前者评估单位是「整次运行」，后者是「单节点」；缺少可比的对照，且 autoresearch 没有公开评测协议（[[autoresearch]]）。
- 「不喂历史」是否反而更稳？autoresearch 只保留当前最优文件，避开了摘要压缩损失（AIDE 的 `Σ(T)`）与经验库污染，但也失去了从失败回退的能力；两种做法的收益差未测。
