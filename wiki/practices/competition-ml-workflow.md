# 竞赛型 MLE 工作流（Kaggle 类任务）

本页把 [[kaggle-getting-started]] 的通用流程整理成可执行的顺序，标出每一步在来源里的做法与位置，并给出**本库的时效性判断**（哪些仍然成立、哪些已过时、哪些从来就没被验证过）。它描述的是人类选手的工作面，但对智能体同样是一份**阶段清单**：知道哪些阶段被人类认为最有价值，才能判断 agent 应该在哪些阶段投入算力（见末节）。

## 七段流程

| # | 阶段 | 来源做法 | 位置 | 时效性判断 |
| --- | --- | --- | --- | --- |
| 1 | 数据探索 EDA | pandas 载入 + matplotlib/seaborn 画图：目标分布、数值变量箱线图、坐标散点图、按标签着色的散点、两两相关图 | L11–L29 | **仍成立**；但见下方「EDA 的可自动化程度」 |
| 2 | 统计检验 | 用检验验证假设的显著性；非 i.i.d. 时注意检验类型选择与显著性解释 | L31–L35 | 方法论仍成立；未给具体检验 |
| 3 | 预处理 | 多表 Join、缺失值、离群点、类别变量表示、浮点精度噪声 | L37–L47 | **仍成立**；浮点精度噪声一条在今天的表格数据里已少见 |
| 4 | 特征工程 | 领域直觉驱动的特征；Feature Importance 做选择；高基数类别用「前 95% + 其他」编码 | L67–L91 | 原则仍成立；工具已换代（现代写法见 [[feature-selection-workflow]]） |
| 5 | 模型选择 | 树模型优先（GBDT/RF/ExtraTrees），非树模型作 Ensemble 多样性来源 | L93–L110 | **已过时**：这是 2016 年表格赛事的格局；文本/图像任务今天的默认是神经网络 |
| 6 | 调参 | 划出验证集 → 粗 `eta` → 搜其余参数 → 降 `eta` → 早停 | L112–L162 | 流程仍成立；参数名与 API 已变（`reg:linear`→`reg:squarederror`、`silent`→`verbosity`） |
| 7 | CV → Ensemble → Pipeline | 见 [[leaderboard-vs-cv]]；Stacking 见下节 | L164–L240 | CV 与 Stacking 部分仍成立；Pipeline 部分已被现代框架覆盖 |

## 每一段的具体判据

**EDA**：来源列的五类图有明确的用途分工（L21–L27）——分布图看是否不平衡；箱线图看数值变量分布；散点图看坐标数据的趋势与离群点；按标签着色看可分性（「对 Feature 的构造很有帮助」）；两两相关图看冗余。可迁移的不是图表类型，而是**每张图要回答什么问题**。

**预处理**：唯一需要留意的细节是浮点噪声——「有些 Float 变量可能是从未知的 Int 变量转换得到的，这个过程中发生精度损失会在数据中产生不必要的 Noise，即两个数值原本是相同的却在小数点后某一位开始有不同」（L45）。这类问题在现代管道里通常被 dtype 与序列化格式解决，但同类问题（编码不一致、单位不一致）依然存在。

**特征工程**：来源的判据是「当一个变量从直觉上来说对所要完成的目标有帮助，就可以将其作为 Feature」，有效性靠画图直观看（L71）。选择阶段看 Random Forest 的 Feature Importance（L83）；脱敏数据上尤其要看，免得琢磨无意义变量（L85）。

**模型**：用 XGB 的主要理由是**速度**——「同样的数据它只需要不到一半的时间就能跑完」（L294）。对以提交次数换分数的竞赛，这是实质收益；对离线一次性建模则未必。

线性/逻辑回归在这份来源里被列为「性能稍逊但适合作 Base Model」（L103–L106）。它们的当代用法与这份 2016 年清单不同：正则强度由估计器自带（`RidgeCV` / `LassoCV` / `LogisticRegressionCV`），预处理要求与默认值陷阱见 [[linear-models-as-baselines]]（依据 [[sklearn-linear-models]]）。**本库判断**：把线性模型当「特征集评估器」比当「最终模型」更匹配它在现代流程里的位置。

**调参**：来源的五步（L135–L141）本质是「先粗后细 + 用早停代替固定轮数」。两条经验值值得记：RF 的 `max_features` 大约取特征数的平方根（L124）；有随机性的模型必须记录种子以便复现（L162）。

**Stacking**：折外预测组装第二层特征、测试侧对各折模型取平均（L190–L194）。这是全文最经得起时间检验的一段工程细节，机制与当代实现一致。

## 四个张力与一个坑

**张力一：特征越多越好，还是越少越好？**

来源同时主张「生成尽量多的 Feature，相信 Model 能够挑出最有用的 Feature」（L77）与「先做一轮 Feature Selection 仍有好处」（L79–L81），而在实战里又遇到**最后一批新增特征让模型明显变差、重做 Grid Search 也救不回来**（L290）。作者把它列为未解决的开放问题（L350），设想的方案是「把使用不同版本特征的模型 Ensemble 起来」（L330，未实施）。

本库的判断（**综合**）：两种说法并不矛盾，但适用条件不同——「多」适用于**信噪比高、样本量足**的情形；当新增特征与已有特征强交互、或本身噪声大时，树的贪心分裂会先抓到噪声。真正缺的是一条**判断「这批特征该留哪些」的流程**：逐组加入 + 固定 CV 划分 + 记录每组的边际收益，而不是一次性全加再调参。

现代实现对应的是 1.13 节的三类选择器（[[sklearn-feature-selection]]）与 [[feature-selection-workflow]]。两个必须补上的限定：① 来源的「Feature Importance 做选择」是 MDI，而 MDI 有训练集统计与高基数偏好两个缺陷，用在 ID 类列上会保留无用列（[[ensembles]], L518）；② 选择器必须放进 `Pipeline` —— 先在全量数据上选再 CV 会让测试折参与选择，不能作为独立泛化评估（[[feature-selection-workflow]]）。

**张力二：CV 与排行榜冲突时信谁？**

见 [[leaderboard-vs-cv]]。结论是：信 CV 的前提是 CV 切分复刻了真实划分的结构（L331）。

现代意义上的「复刻结构」在 API 层是三条具体选择（[[cross-validation-design-and-tuning]]，依据 [[sklearn-cross-validation]]）：① 训练集与测试集共享实体 → `GroupKFold`（保证同一组不跨训练/测试折，[[sklearn-cross-validation]], L425–L454）；② 按时间划分 → `TimeSeriesSplit`；③ 稀有类 → `StratifiedKFold`（来源的「5-Fold 提到 10-Fold」本质上是在缓解单次划分的方差，而分层会**人为压小**折间方差，L361–L365）。

**张力三：5-Fold 提到 10-Fold 提高了什么？**

作者因 LB 与 CV 反复背离，「将 5-Fold 提到 10-Fold，然后以 CV 为标准继续前进」（L298）。注意这提高的是**CV 分数的估计精度**，不是模型性能；折数增加让单次划分的方差变小，代价是训练时间线性增加（L168）。

**张力四：`raw features only` 的强模型 vs 「Feature 为王」**

2016 年的入门指南把「Feature 为主，调参和 Ensemble 为辅」当作主线（[[kaggle-getting-started]], L69），并把大部分时间投在造特征上。十年后的同一系列帖子里，一名第一名选手用**不造任何新列**的 21 个原始列，让一个 token 化的 transformer 与调参 XGBoost 打到同一水平（[[kaggle-q-ft]], L22、L142–L143）。但同一系列的第二篇又给出反向读数：**同类人工特征对 transformer 只值 +4e-4，对 GBDT 值 +1.6e-3**（[[kaggle-q-ft-v2]], L100）。

**本库综合**：这不是“特征工程过时了”，而是**人工特征与模型内建表征互相替代**——当模型能逐列学查找表与交互时，counts、路由画像这类统计量的边际收益会下降；但“知道这列是什么”（编码方式、词表粒度、缺失/延迟的桶边界）仍然是收益的主要来源，只不过它从“造新列”变成了“设计 tokenizer”。可操作判据：模型已有逐列嵌入（GBDT 的类别处理、FT-T、Q-FT）时，先把预算投到编码与验证设计；模型只能看到扁平数值向量（线性模型、小 MLP）时，人工特征仍是主要杠杆。

**补充纪律：单折试点 ≠ 全折 OOF**。同一系列两篇各给了一个读数：fold-0 比 5 折 OOF 高 **+6.5e-4**（[[kaggle-q-ft]], L129 vs L142）与 **+1.8e-4**（[[kaggle-q-ft-v2]], L145 vs L30）。而两篇里被当作结论的改进量恰好也在 3e-4–1e-3 量级——也就是说，**在一折上看到的“提升”很容易是整个消融链里最大的一次抽样噪声**。

**第三篇的读数**：同一赛题的方案帖把顺序平均曲线画在 **fold-0 AUC** 上，最高点 **0.96265** 反而高于全篇所有 OOF 数字（最高 0.96245），而同一模型的全折报告是 **0.96242**（[[kaggle-tfms-llms-tabular]] L212、图 `orders_curve.png`）。所以「单折比 OOF 高」已累积三个同向读数（+6.5e-4、+1.8e-4、+1.8e-4 ~ +2.3e-4），且后两篇都**把单折数字报在最显眼的位置**。

**一个坑：合并训练集与测试集做预处理**

来源在 Home Depot 里「将训练集和测试集合并，并与产品描述和属性 Join 起来」，理由是「后面有一系列操作，如果不合并的话就要重复写两次」（L265）。按现代口径这是需要显式论证的做法（**综合**，非来源陈述）：把 `fit` 暴露给测试数据会让无监督变换（词表、统计量、离散化边界）带上测试集信息，CV 分数与 LB 的语义随之变化。若采用，至少应（a）确认变换不含标签信息，(b) 记录该选择对 CV 分数的影响，(c) 在最终管道里用 `fit_transform(train) → transform(test)` 复现。

## 两个新阶段：生成过程逆向与 pair 协作

### 把生成过程当建模对象（合成赛题特有）

Playground 这类合成赛题多出一个可选阶段：**逆向数据的生成过程**。[[kaggle-tfms-llms-tabular]] 的做法是先用三条行为证据把生成器认定为 GReaT 且「标签最先写出」（tokenizer 指纹、温度/top-k 设置、label-first 能复现标签率，L195–L204），再直接训练一个「给定标签生成整行」的模型并用 Bayes 反转，取得 **0.96242**，高于调参 XGBoost 的 **0.96149**（L212、L219）。

可执行清单（**本库综合**，来源未写成流程）：

1. **先判数据是不是合成的**：字段分布过于规整、取值集合不自然、tokenizer 指纹、重复与舍入痕迹；
2. **若能猜出生成器**，就用**它的文本序列化格式**写行（列名、分隔符、小数位、缺失写法）；
3. **训「先标签后特征」的似然模型**，对每个候选标签打分并用 Bayes 反转；
4. **在真实数据上不要默认这条红利**——来源没有任何非合成对照，而它自己的解释就是「因为数据是被 LM 写出来的」（L158）。

**纪律**：这类逆向胜利是**赛题特异的**，不能当作模型更优的证据；判定生成器身份的证据也都是行为性的（任何以 GPT-2 为骨干的生成器都会留下同样的指纹，见来源页分歧 10）。

### 共享 OOF/test pair：一种可复用的协作与预算机制

该帖的 245 对 pair 来自社区共享，全部用同一套 `StratifiedKFold(5, shuffle=True, random_state=42)`，因此可直接进同一个逻辑回归（L162–L168；协议细节见 [[ensembles]]）。这是竞赛后期最像**工程流程**的一段：

| 环节 | 要求 | 不做的代价 |
| --- | --- | --- |
| 交付物粒度 | 「OOF + test」成对，**同一套折划分** | 无法入池 |
| 元数据 | 模型名、种子、早停轮数、是否用过测试特征/外部数据 | 池的 CV 无法校正，别人会误用 |
| 报告口径 | 逐折数组 + 合并 OOF，不只报单值 | 「单折 vs OOF」混淆（见上一节） |
| 入池前自查 | 与池内成员是否同族、是否只多一层换皮 | 同族堆叠几乎不涨（9 个 TFM stack 只 +5e-5） |

对智能体场景的意义（**本库综合**）：pair 把「训一个基模型」与「要不要进 stack」解耦，是一种**可并行、可验证的最小交付物**——多 agent 各自交 pair，中心用同一条协议合并，比让一个 agent 串行训练十几个模型更现实。单人复现不了 245 对，但这条协议在多人/多 agent 下可行。

## EDA 的可自动化程度（对智能体场景的映射）

这是本页对 AutoResearch 最直接的一节，全部为**本库综合**。

| 阶段 | 人类成本 | 可自动化程度 | 依据 |
| --- | --- | --- | --- |
| EDA / 看图表 | 高，依赖肉眼与领域知识 | 低 | 来源全靠人工看图得出结论（L21–L29） |
| 预处理 | 中 | 中高 | 规则明确，但「合并 train/test 是否安全」需判断（L265） |
| 特征构造 | 最高（作者自评「花在 Feature 上的时间还是太少」，L339） | 低—中 | 依赖领域洞见；来源的收益主要来自这里 |
| 特征选择 | 低 | 高 | 看 Feature Importance 即可（L83） |
| 调参与 CV | 中，但可并行 | 高 | 来源的调参流程是固定的五步（L135–L141） |
| Ensemble / Stacking | 中 | 高 | 机制固定（L190–L194） |
| 赛后复盘 | 中 | 低 | 依赖阅读他人解法与领域判断（L321–L331） |

对照 [[aide]]：AIDE 明确放弃 EDA，只给「行数、列名、划分」这类数据预览（[[aide]], p. 4），把预算全部投在特征与模型搜索上。本页的表格解释了它为什么可以这么做——**EDA 是人类的强项、也是人类时间的主要去处，但在一个有固定评估器的竞赛里，它不直接产出提交**。反过来，这也给出一个可检验的预测：当评估器不可信或任务结构不明（真实项目而非竞赛）时，跳过 EDA 的代价会上升到无法承受。

## 适用与版本

- **适用**：表格型或中小规模结构化数据、有固定单一评分的任务；单机可跑；以「多次提交」为工作模式。
- **不适用**：以深度学习为主的任务（文本/图像/序列）。来源自己也标注「跟图像有关的比赛中神经网络的重要性还是不能小觑」（L101），但整篇文章不覆盖这类工作流。
- **代码不能照抄**：正文片段的 API 已被移除，等价写法见 [[kaggle-getting-started]] 的「代码与 API 时效性」表。
- **证据强度**：全部结论来自一名选手的一次比赛 + 一次入门经历，无对照、无方差、无复现。

## 待解问题

- 「逐组加入特征并记录边际收益」这条流程有没有公开的对照记录？来源只有「全加 → 变差 → 调参无效」的一次观测（L290）。
- 合并 train/test 做无监督变换，在 2016 年的赛事里是否真的带来了分数收益？来源未做 A/B。
- 现代表格任务的默认流程（LightGBM/CatBoost + 目标编码 + k 折 + seed averaging）与本文的差异，现在由 [[ft-transformer]] **部分覆盖**：同协议比较、GBDT vs DL、FT-T 与 ResNet 基线。但该来源以数值特征为主（11 个数据集中只有 Adult 有类别特征）、无缺失值实验，因此类别特征/缺失值/多划分下的默认流程仍需新来源。选型见 [[tabular-model-selection]]，对照见 [[gbdt-vs-tabular-dl]]。
- 来源的七段流程是否遗漏了「赛题理解/泄漏排查」这类阶段？作者在 EDA 里提到了「产品 ID 会不会导致 Overfitting」（L257），但流程图上没有对应步骤。
- 「生成过程逆向」能不能在赛前自动化：能不能用一个分类器判「这份数据是否由 LM 生成、用的是哪个 tokenizer」？
- pair 池协作在多 agent 里会不会出现「互相污染折划分」的新问题？
