# 科研智能体 Harness 设计（树搜索 / 单循环 / 多项目三形态）

面向「可执行、可评估、可迭代」任务搭建研究型 agent 时的工程指导。本页区分三种 harness 形态：**树搜索脚手架**（AIDE，[[aide]]）、**单任务搜索循环**（Hyra-1.0，[[hyra-1-0]]）与**多项目长周期组织**（Hyra 2.0，[[hyra-2-0]]）。先给来源论述，再给本库的落地建议，两者明确分开。

## 形态零：树搜索脚手架（AIDE）

AIDE 是三者中唯一有公开实现与形式化定义的：把机器学习工程写成代码优化问题 `s* = argmax h(s)`（式 (1)，[[aide]], p. 2），每轮「提议 → 评估 → 挂树 → 换基准」（算法 1，p. 3）。

1. **状态是一棵树，不是一段对话**：节点 =（脚本, 分数），边 = 一次改进尝试；根解为空脚本（p. 3）。作者明确对照 ReAct 式做法：把全部历史观测不断追加进 context（append 式）会撑爆窗口（p. 2）。
2. **策略硬编码、可预测**：draft 直到初始解数量达标 → debug 未超深度的 bug 节点 → 否则 improve 当前最好的非 bug 解（p. 3）。代价是没有探索/利用的显式权衡，也没有「换路线」的机制。
3. **编码算子拆三种入口**：draft（先写方案再写单文件程序）、debug（保留思路修 import/张量维度）、improve（**恰好一个原子改动**，使效果可直接测量）（p. 3–4）。
4. **摘要算子代替全量历史**：`Σ(T)` 只回填性能指标、超参设置与调试线索，使节点「无状态」但又继承先验（p. 4）。
5. **prompt 里带数据预览**：行数、列名、划分等元数据常驻，不做完整 EDA，但足以支撑验证集划分与超参缩放（p. 4）。
6. **接口沿用人类竞赛形态**：产出 `submission.csv`，评测方掌握隐藏标签（p. 5）。

适用边界：单文件、单次可评估、反馈分钟级到小时级的任务（Kaggle 类表格/深度学习竞赛）；需要跨文件重构或多步交互的任务上明确失效（RE-Bench，p. 9）。

## 形态一：单任务搜索循环（Hyra-1.0）

1. **原则对齐 The Bitter Lesson**：框架尽量轻量简单，智能体的动作空间尽量广阔（[[hyra-1-0]], section "Hyra Harness"，原文 `raw/articles/Hyra.md:25`）。
2. **统一循环**：给定任务描述后持续「基于历史经验提出更好的 solution」，经验包含过往运行日志、评估器反馈与源码；终止条件为 Agent 主动结束或预算耗尽，最终返回历史最优方案（同上）。
3. **角色分离**：
   - Context Agent 维护 [[experience-bank]]，把 solution 与评估结果入库，并合成灵感投入任务队列（`raw/articles/Hyra.md:27`）。
   - 多个 Proposal Agent 各自领取灵感、写出 `solution/`（入口脚本 `solve.sh`）、在**全新沙盒**中运行与评分（`raw/articles/Hyra.md:28`）。
4. **异步生产者-消费者**：Context Agent 填队列、Proposal Agent 抽队列，结果回写 EB；用信号量控制沙盒、模型推理与队列资源「健康地满载」（`raw/articles/Hyra.md:30`）。
5. **无评估器时双层循环**：内层优化 solution，外层优化评估器（`raw/articles/Hyra.md:32`，详见 [[evaluator-solution-co-evolution]]）。

适用边界（本库归纳）：单轮以分钟到小时计、反馈可自动获取、评估器可固定或可迭代的任务。

## 形态二：多项目长周期组织（Hyra 2.0）

来源明确说明动机：训练一个模型要经历方案设计、代码实现、训练、评估与反复修改，可能持续**数天到数周**；多项目并行还要处理实验等待、资源分配与研究方向的调整，「这些工作很难靠一个不断延长的 agent session 来管理」（[[hyra-2-0]], section "为升级工具而生的 Harness"，`raw/articles/Hyra 2.0.md:63`）。

### 1. 三层角色 + 可被质疑的执行者

| 角色 | 职责 | 关键设计点 |
| --- | --- | --- |
| Overall | 与人类沟通、定优先级、协调资源与关键决策 | 唯一对外的接口，避免人类被多处打断 |
| Mission | 长期负责一个研究问题：路线、实验设计、组织 Worker、对结论负责 | 承担「何时换方向/哪些结果需复核」的判断 |
| Worker | 读代码、做实验、分析失败、提新想法 | **可以质疑 Mission**；不同 Worker 可用不同模型 |
| Review Worker | 独立验证 | 从原始问题与证据入手，减少执行者结论的锚定 |

（`raw/articles/Hyra 2.0.md:67`、`:77`。）

### 2. 持久化队列 + 显式唤醒

- 任务进入持久化队列，调度器按**优先级、依赖关系、资源上限**启动 Worker（`raw/articles/Hyra 2.0.md:69`）。
- 等待训练结果或人工审批时，其他任务继续；agent 可**设置下一次唤醒时间**，在实验完成或到达检查节点后接着工作（同上）。
- （综合）含意：状态必须落在外部存储，不能靠「一个长上下文」延续；「等待」是一等状态而非阻塞。

### 3. 协作记录：异步默认、通知例外

Research Board 记录想法、实验发现、证据与关键决策；普通进展由其他 agent 异步阅读，**必须处理**的问题才走消息通知，且接收方须明确回应（`raw/articles/Hyra 2.0.md:71`）。这样 Worker 能连续工作较长时间，Mission 也能查到各条路线的进展而不必频繁打断。

### 4. 证据随报告提交

Worker 汇报完成时须附**代码版本、实验结果、日志或原始运行轨迹**；Mission 可查看实际操作记录，核查实验是否支持报告中的结论（`raw/articles/Hyra 2.0.md:77`）。这条把「我完成了」变成了可审计的断言。

### 5. 人工审批门

接入真实研发环境时，涉及**较大算力开销**与**共享知识同步**的操作需人工审批，已获准的工作由系统继续推进（`raw/articles/Hyra 2.0.md:65`）。换句话说，自动化边界由成本与影响范围决定，而不是由「模型能不能做」决定。

### 6. 记忆分层与知识分级

项目状态（队列 + Board）、每个 agent 的分层记忆、跨任务 Books 分开保存；Books 条目分级为观察/已验证/约定，约定需人类确认（`raw/articles/Hyra 2.0.md:81-83`，详见 [[research-memory-tiers]]）。

## 三形态对照

| 维度 | AIDE（树搜索） | Hyra-1.0（单循环） | Hyra 2.0（多项目） |
| --- | --- | --- | --- |
| 状态载体 | 解树 + `Σ(T)` 摘要（有损压缩） | 经验库 EB（全量 solution/日志/源码）+ 灵感队列 | 队列 + Research Board + 分层记忆 + Books |
| 选点策略 | 硬编码 draft/debug/improve | 灵感驱动，多 Proposal Agent 竞争 | Mission 分派，Worker 独立执行、可质疑 Mission |
| 并发 | 单树串行推进（论文未描述并行） | 异步生产者-消费者 + 资源信号量 | 多 Mission/Worker 并行，按资源上限调度 |
| 失败的处置 | debug 有限深度，超限则弃枝 | 失败日志进 EB，成为后续灵感素材 | 复核者独立验证，允许「只能支持更窄结论」 |
| 时间尺度 | 分钟–小时（MLE-Bench 24h 窗口） | 小时–天 | 天–周（含等待与审批） |
| 公开证据 | 论文 + 开源实现 + 第三方基准 | 厂商博客，无实现 | 厂商博客，无实现 |

（来源：[[aide]], p. 3–5、p. 8；[[hyra-1-0]], `raw/articles/Hyra.md:25-32`；[[hyra-2-0]], `raw/articles/Hyra 2.0.md:63-85`。表内归纳为本库综合。）

## 可迁移的工程要点（综合）

### 对树搜索形态

- **把「改动粒度」写进规格**：improve 只做一处改动，是 AIDE 归因能力的来源；若允许一次改多处，必须额外提供等价的可归因机制（对照实验、diff 审计），否则分数变化无法解释。
- **摘要与全量分开存**：喂给模型的 `Σ(T)` 可以有损，但树本身必须持久、可回放；否则无法复算历史最优。
- **给策略留一条「重新开始」的出口**：只有 draft/debug/improve 的硬编码策略会在多步交互任务上困在局部最优（RE-Bench，p. 9）；工程上应显式设置「换路线」动作或外部触发。
- **评测方能掌握隐藏标签**：agent 只见输入、提交 `submission.csv`，由外部打分（p. 5）——这条比在 prompt 里要求「不要作弊」有效得多。

### 对单循环形态

- **动作空间优先于流程复杂度**：能直接写代码、跑实验、读日志，就不必为每类任务设计专用 DSL；轻量 harness 的代价是必须把「评估与沙盒」做扎实。
- **解耦思考与执行**：proposal 生成（模型调用，贵）与沙盒执行（CPU/GPU，贵但可并行）分别限流；信号量至少覆盖并发沙盒数、模型并发数、队列长度三类资源。
- **每个 solution 都在干净沙盒里跑**：共享工作区会让「成功」混入未记录的副作用，也让失败无法归因。
- **入口约定固定**（如 `solve.sh` + `solution/` 目录）：评估器面向稳定契约，proposal 侧可自由换语言与结构。
- **终点判定显式化**：Agent 主动结束 + 预算耗尽两条路径都要有，并定义「历史最优」的选取口径（同一评估器版本内比较）。
- **保留可重放证据**：日志、源码、评估器版本三者一起入库，否则最优结果无法复算。

### 对长周期形态

- **状态外置**：队列、看板、实验产物、审批状态都必须可从中断处恢复；进程重启不应丢研究进度。
- **把「等待」建模成事件**：训练任务、审批、外部评测都会挂起数小时到数天；用唤醒时间 + 检查节点替代轮询或阻塞会话。
- **角色权限最小化**：只有 Overall 对外沟通，只有 Mission 做方向决策，Worker 默认不能花大钱；审批门挂在「成本高」与「影响他人」两类动作上。
- **复核者与被复核者信息隔离**：复核从原始问题与证据起步，避免继承执行者的结论框架；复核结果允许「只能支持更窄结论」，不要强行收束为通过/不通过。
- **记录分三层写**：发生了什么（看板）、我当前相信什么（agent 记忆）、别人可以怎么复用（Books）。混写会让记录既不可读也不可复用。
- **知识要带成熟度与适用条件**：没有独立复现的现象只能标为观察；影响他人行为的结论必须人工确认。

## 适用与不适用

- 适用（树搜索）：有明确执行入口与可自动打分的短程任务——训练 recipe 搜索、kernel 优化、组合优化、结构化产物生成；解能写成单文件脚本时收益最大。
- 适用（单循环）：只需一个稳定入口（`solve.sh` + `solution/`）即可，不要求单文件；代价是评估器与沙盒要自己搭（综合）。
- 适用（长周期）：目标需要多轮实验、跨天等待与多路线并行的工具/模型研发，且组织上能提供审批与复核人力。
- 谨慎：评估成本高于生成成本的任务（异步流水线的收益被稀释）；缺乏客观判据、只能靠人判断的领域（复核成本会主导总成本）。
- 不适用（树搜索）：需要跨文件重构、长程多步交互、或在单一节点内无法表达的任务（RE-Bench 的 Rust CodeContests，`raw/extracted/2502.13138v1.md:510-539`）。
- 不适用/需改造：目标只能由人判断且反馈稀疏的场景；此时外层循环要引入用户反馈，并接受偏好漂移风险。

## 版本与时效

- 三个形态的证据强度不同：AIDE 有论文、形式化定义、开源实现与第三方基准；Hyra 两个版本都只有厂商博客表述，且 2.0 无配套实现，因此「可迁移要点」为本库整理，非来源原话。
- AIDE 论文未公开 harness 超参（初始解数量、调试深度、总步数），复现需读仓库；2.0 未披露失败率、人工介入频率与成本。
- 树搜索形态的「单文件脚本」前提是其边界，不是普适最优：换到多文件代码库需要重新设计算子。

## 待解问题

- 树搜索与单循环是否只是同一件事的两种实现？AIDE 的「解树 + 摘要」与 Hyra 的「经验库 + 灵感」都把历史当作选点依据，差别在压缩方式与是否并发；目前没有同预算的对照。
- AIDE 的初始解数量、调试深度、总步数与每节点时限均未公开（p. 3–4 只有规则描述），因此「原子改动 + 树搜索」的收益无法按预算复算。
- 贪心策略的平台期是否只由策略造成？图 4 显示 AIDE 约 5 小时后走平（p. 9，已目视核查），但没有「换策略」的对照组。
- 1.0 与 2.0 的 harness 是替代、超集还是并存？剪藏未说明。
- 灵感合成（1.0）与 skill 提取（2.0）的具体算法均未披露。
- 队列的优先级与抢占策略、资源上限的实际参数未披露；「等待审批时继续其他任务」在算力饱和时如何调度未知。
- 长周期项目的失败如何判定与回收（预算耗尽、方向错误、复核推翻）？来源只描述了机制，没有失败案例。
- 人工审批的频率有多高？若每个项目需要多次审批，「更经济」的主张需重新核算。
