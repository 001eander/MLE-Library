## 概要

`autoresearch` 是一个「小规模但真实」的 LLM 训练环境 + 一份给编码智能体的指令，让智能体在自己所在的仓库里反复做实验：改 `train.py` → 训练 5 分钟 → 看验证损失是否变好 → 保留或丢弃 → 重复（[[autoresearch]], L19）。训练代码是 nanochat 的简化单 GPU 实现（L19）。

它与本库已收录的四份来源的关键差别是**「人改什么」被换掉了**：人类不再直接编辑 Python，而是编辑 `program.md` 这份给智能体的 Markdown 指令，来源把这称为「搭建你的自主研究组织」（L19），并说 `program.md`「实质上是一个超轻量级的『技能』」（L61）。

> 剪藏 L17 是一段**讽刺性序言**（「肉计算机」「该代码库的第 10,205 代」「自我修改的二进制文件」）。它是玩笑，不是对当前能力的陈述，本页不据此做任何推断。

## 关键主张

### 1. 三个文件的契约：只有 `train.py` 可改

| 文件 | 角色 | 谁修改 | 位置 |
| --- | --- | --- | --- |
| `prepare.py` | 固定常量、一次性数据准备（下载数据、训练 BPE 分词器）、运行时工具（数据加载器、评估） | **不修改** | L25、L66 |
| `train.py` | 完整 GPT 模型、优化器（Muon + AdamW）、训练循环；架构、超参数、优化器、批大小等全部可调 | **智能体** | L26、L67 |
| `program.md` | 面向单个智能体的基线指令 | **人类**，并随实验迭代 | L27、L68 |
| `pyproject.toml` | 依赖 | — | L69 |

- 设计理由是「把范围保持可控、代码差异便于审查」（L74）。
- 注意 `prepare.py` 同时承担**评估**职责（L25「运行时工具（数据加载器、评估）」）：评估代码位于禁改文件内，这一点在「评估器与解分离」上是正面设计（**综合**）。

### 2. 人类优化的是指令，不是代码

- 来源明确反对常规切入点：「你不再像通常作为研究者那样直接改动任何 Python 文件。相反，你要编写 `program.md` Markdown 文件，为 AI 智能体提供上下文，并搭建你的自主研究组织」（L19）。
- 默认 `program.md` 是「有意保持为极简基线」；至于**如何随时间迭代它以找到实现最快研究进展的「研究组织代码」**、如何加入更多智能体，来源只说「显然都是可以做到的」（L19）——这是**未经验证的外推**，剪藏没有任何迭代记录或对照。
- 运行方式是「在这个仓库中启动你的 Claude、Codex 或任何你想用的工具（并禁用所有权限）」，提示语只有一句「请先查看 program.md，然后开始一项新实验！先完成环境配置」（L55–L59）。

### 3. 固定 5 分钟墙钟预算：可比性来自预算，而不是步数

- 训练「采用固定的 **5 分钟时间预算**（实际耗时，不含启动和编译时间），无论你的算力细节如何」（L29）。
- 吞吐口径：「大约每小时 12 次实验，睡眠期间大约 100 次实验」（L75）。
- 来源自己给出两个好处与一个代价（L75）：
  - 好处一：无论智能体改什么（模型大小、批大小、架构），实验**直接可比**；
  - 好处二：autoresearch 会在这段时间预算内**为你的平台找到最优模型**（即结果是平台特定的最优点）；
  - 代价：**与其他平台上运行的结果无法比较**。
- 预算语义是**墙钟时间**，不是步数、token 数或 FLOPs（L29）。因此「一次实验」在不同硬件上对应的算力并不相同（**综合**）。

### 4. 指标 `val_bpb`：与词表大小无关

- 指标是 `val_bpb`（验证集每字节比特数），越低越好，并且「与词表大小无关，因此可以公平比较架构变更」（L29）。
- 拆开看是两件事（**综合**）：(a) BPB 把损失折算到字节粒度，因此换分词器不会仅因词表大小改变分母；(b) 「越低越好」让 keep/discard 判定无歧义。剪藏未给公式、未说验证集如何切分、是否另留 holdout。

### 5. 搜索结构：单链贪心，没有树也没有种群

- 循环是「修改代码，训练 5 分钟，检查结果是否有提升，保留或丢弃，然后重复」（L19）；产物是「一份实验日志」和一个（但愿更好的）模型。
- 剪藏没有描述任何树结构、种群、父节点、摘要算子或回放机制；记忆载体只有**工作区里的当前文件**与**实验日志**（L19、L74）。
- 与 AIDE 的差别不只是「没有树」（**综合**）：AIDE 每次只做一处原子改动以便归因（[[aide]], p. 4），而 autoresearch 的保留/丢弃判定基于**整次运行**的结果，改动可以同时触及多处（图内被保留的标签里就有复合改动，见下节）。

### 6. 平台与规模是硬边界

- 目前要求一块 NVIDIA GPU；作者认为支持 CPU、MPS 在原理上完全可能，但「也会使代码膨胀」，且「并不 100% 确定自己是否想亲自承担这项工作」（L80）。父级 nanochat 仓库被指为更广平台支持的参考（Flash Attention 3 回退实现、通用设备支持、自动检测等，L80）。
- 依赖与复杂度：「除 PyTorch 和少数小型软件包外，没有外部依赖。没有分布式训练，没有复杂配置。一个 GPU、一个文件、一个指标」（L76）。
- 给小机器的 7 条降规模建议（L84–L90，逐条见 [[autoresearch-repo]]）：
  1. 换熵更低的数据集（TinyStories，GPT-4 生成的短篇故事），让更小的模型也能出合理结果（L84）；
  2. 降 `vocab_size`：8192 → 4096 / 2048 / 1024，甚至字节级（256 种 UTF-8 字节）（L85）；
  3. 大幅降 `MAX_SEQ_LEN`（可到 256），并用增大 `DEVICE_BATCH_SIZE` 补偿（两者乘积是每次前向/反向的 token 数）（L86）；
  4. 减小 `EVAL_TOKENS`（L87）；
  5. `DEPTH` 默认 8，可降到 4 左右，因为许多变量是它的函数（L88）；
  6. `WINDOW_PATTERN` 从 `"SSSL"`（交替带状注意力）改为 `"L"`，因为前者在小设备上可能很低效（L89）；
  7. 大幅降 `TOTAL_BATCH_SIZE`，但保持 2 的幂，例如 `2**14`（约 16K）（L90）。
- **内部张力（综合）**：第 3、4 条要求改 `prepare.py`，而 `prepare.py` 是「不要修改」的文件（L25、L66）。也就是说降规模是**人类对基线的改写**，不是智能体可做的动作；改写后不同机器上的「同一实验」更不可比。

### 7. 快速开始（L37–L51）

`uv` 安装 → `uv sync` → `uv run prepare.py`（一次性，约 2 分钟）→ `uv run train.py`（约 5 分钟）。四步都能跑通，说明环境可用。

三点必须标注的限制：

- **该图是仓库 master 的当前文件**，抓取时间晚于剪藏；README 正文（L15）只把它当「项目概览」，**未解释**统计口径、运行的硬件、agent 模型或时间。
- 它是**单次运行**：没有方差、没有多种子基线与重复，也没有把 15 次保留与 68 次丢弃做统计检验。
- 读数为目视近似，图上没有数据表；长标签在斜向排布下被截断（如 `aspect_ratio 57` 的后半句）。

**一个强信号（本库推断，非来源表述）**：被保留的改动里包含 `random seed 42→137`。若仅换随机种子就能被判定为「提升」，说明 5 分钟预算下 `val_bpb` 的**种子噪声与改进幅度同量级**，那么 15 次「保留」中可能有一部分是噪声选择（winner's curse）。这条直接对应 [[evaluator-design-and-reward-hacking]] 里「在固定验证集上诚实而密集地优化」的失效模式，已列入 [[automated-research-open-questions]]。

## 局限

### 1. 证据形态

- **仓库 README**，不是论文、不是评测报告：没有方法章节、没有消融、没有第三方复现。正文**一个结果数字都没有**；唯一的量化信息来自 README 未加解释的 `progress.png`。
- 无 commit、tag 或日期化的版本，因此「今天的 autoresearch」与本页描述的剪藏可能已不同；agent 侧模型（Claude / Codex / 其它）无版本，无法归因「是 harness 还是模型」。
- 与本库其它来源不同，它有**公开实现**（这是强项），但没有可引用的评测协议。

### 2. 预算与可比性的自限

- 「5 分钟」是墙钟，硬件越慢，同一时长内能完成的优化步数越少；因此来源自己承认**跨平台结果不可比**（L75）。这也意味着「夜间 100 次实验」是平台特定的吞吐，不是通用数量级。
- 小机器上的 7 条建议会同时改变数据分布（TinyStories）、词表、序列长度与模型深度，改动维度过多，**无法归因**是哪一项带来收益（**综合**）。

### 3. 评估设计缺位

- 剪藏未提验证集切分方式、是否有 holdout / private 集、是否防「在验证集上搜索」；而 keep/discard 的判定完全建立在这一个标量上（L19、L29）。
- 未提 reward hacking 防护、作弊检测或人工复核；`prepare.py` 禁改把评估代码与可改代码分开了，这是结构性防护，但来源没有把它解释为防护（**综合**）。

### 4. 安全姿态

- 来源建议「禁用所有权限」（L55）后让智能体自由改训练代码并反复执行。剪藏未讨论沙箱、资源上限、失败回滚、成本上限或人工审批；与本库 [[research-agent-harness]] 记录的审批门（[[hyra-2-0]]）形成鲜明对比。
- 这在个人机器上可以接受（因为损失上限是「跑坏一晚」），但在共享集群上不成立（**综合**）。

### 5. 主张与外推

- 「如何迭代 `program.md` 以找到最快进展的研究组织代码」「如何加入更多智能体」都被称为「显然可以做到」（L19），但没有任何实现或数据；属**假设**，不可当作已验证结论。
- L17 的「第 10,205 代」「自我修改的二进制文件」是讽刺，不能作为递归自我改进的证据。

### 6. 元数据瑕疵

- `published: 2026-03-07` 只见于剪藏 frontmatter，GitHub 页面本身通常不提供该字段；本页标注为「剪藏口径，未独立核实」。
- 剪藏把图片存成外链（L15），未随剪藏保存；本次另行抓取并入库。

## 待解问题

- **噪声底有多大？** 5 分钟固定预算下，同一配置换随机种子的 `val_bpb` 波动范围是多少？若与 `random seed 42→137` 的收益同量级，15 次保留里有多少是真改进？
- **验证集是否被搜索？** 是否有独立 holdout？若 keep/discard 只看同一个 `val_bpb`，长期运行会以多快速度过拟合？
- **5 分钟是「等价算力」吗？** 同一 harness 在 H100 与消费级 GPU 上，5 分钟内可完成的优化步数相差多少？「本平台最优」与「迁移到别的平台仍最优」差多远？
- **实验日志的形态**：是纯文本、结构化表、还是 git 提交历史？是否保存每次改动的 diff，能否复算被丢弃的实验？
- **降规模后还剩什么**：换 TinyStories + 深度 4 + 词表 1024 之后，实验仍在验证「训练 recipe」这一命题吗，还是退化成「在一个玩具数据集上调参」？
- **多智能体组织**：L19 提到「如何加入更多智能体」，但剪藏没有任何队列、分工或冲突处理机制（对照 [[hyra-2-0]] 的 Overall/Mission/Worker）。
- **`progress.png` 对应哪次运行**：commit、硬件、agent 模型、起止时间、是否连续跑完 83 次实验（有无中断/重启）？
- **成本**：83 次实验 = 约 83 × (5 分钟 + 启动/编译) 的 GPU 时间，加 agent 的 token 成本；剪藏未给任何成本口径。
